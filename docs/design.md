# 设计说明

## 一、要解决的问题

用大模型帮忙写 Linux 上机实验报告，效率提升明显，但引入了一个新风险：

> **模型会把没发生的事写成发生了。**

具体表现有三种：

1. **数字篡改** —— `libadd.so` 实际 7880 字节，模型写成 9999 字节
2. **编造依据** —— 凭空写一段"看起来像终端输出"的文字作为证据
3. **数量不符** —— 9 个步骤只返回了 8 条，或把第 3 条的内容安到第 5 条上

前两种最难发现，因为**读起来是通顺的、专业的**，人工通读时不会停下来核对每个数字。

## 二、核心思路

把"是否有据可依"从**开放判断**变成**机械比对**。

具体做法：要求模型每写一条描述，必须附一段 `source_output` ——
从给定的真实终端输出中**逐字复制**的原文片段。校验器随后做一次比对：

```
normalize(source_output) in normalize(original_output)  →  通过
否则                                                    →  FABRICATED_SOURCE
```

归一化会去掉空白、统一全半角标点、忽略大小写，所以跨行的引用也能正确匹配。

这个设计的妙处在于：**模型可以写得不好，但不能伪造证据。**
它的解释质量由人判断，但它引用的事实由机器把关。

## 三、三级流水线

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  LLM 生成     │ ──▶ │  规则校验     │ ──▶ │  人工终检     │
│  写描述       │     │  查矛盾       │     │  查准确性     │
└──────────────┘     └──────────────┘     └──────────────┘
   不确定              确定                  需要人
```

**第一级：LLM 生成。** 只负责把终端输出翻译成通顺的中文描述。它不承担验证责任。

**第二级：规则校验。** 纯确定性逻辑，不调 LLM。分三级：

| 级别 | 含义 | 动作 |
|---|---|---|
| ERROR | 硬矛盾（编造、缺失、数量不符） | 阻断，退出码 2 |
| WARNING | 存疑（数字无出处、疑似空话） | 标记，人工确认 |
| INFO | 提示（描述过短） | 仅记录 |

**第三级：人工终检。** 输出一页带勾选项的 Markdown，把需要人看的部分集中起来，
人不用通读全文，只需要逐条勾选。

## 四、关键决策与理由

### 4.1 校验层为什么不调 LLM？

如果用 LLM 判断"这段描述是不是幻觉"，就是**用不确定的判断去校验不确定的输出**，
校验结果本身也无法复现。

本项目让校验层是纯规则函数：`normalize` + `in` + 集合差集。
同一份输入必然得到同样的输出，可以写进 CI 当断言用（见 `tests/test_e2e.py`）。

### 4.2 为什么强制输出 `source_output`？

三个理由：

1. **可机械校验** —— 一旦证据是"逐字复制的原文"，就能用字符串包含判断真假
2. **约束模型行为** —— prompt 里明确要求"逐字复制"，实测模型会照做
3. **责任显式化** —— 模型必须为每句话指出依据，不能空口断言

### 4.3 为什么用标准库而不是 requests？

- `git clone` 完就能跑，不需要装包
- HTTP 层的重试、退避、错误分类（4xx 不重试 / 429 和 5xx 重试）自己实现更可控
- 没有依赖意味着没有版本冲突，CI 配置简单

### 4.4 为什么保留人工终检这一级？

自动校验只能发现"与日志**矛盾**"的问题，发现不了"虽然一致但解释得**不准确**"。

比如模型说"编译生成了动态库"，日志里确实有 `libadd.so`，
但如果步骤其实是"移动文件"，这句话就虽然有据、却是错的。

这类问题必须靠人。工具的价值是**把人的注意力集中到需要判断的地方**，
而不是替人做判断。

## 五、模块划分

```
llm_report/          —— LLM 交互层（可能出错，需要重试和容错）
  client.py            HTTP 调用、重试退避、JSON 稳健提取
  prompts.py           模板与结构化解析
  cli.py               编排入口

validator/           —— 规则层（确定性，可当断言用）
  checker.py           归一化、比对、报告生成
```

分层的意义在于：**只有 `llm_report/` 是不确定的**。
`validator/` 可以被独立测试、独立信任。

## 六、测试策略

| 测试 | 是否需要 API key | 验证什么 |
|---|---|---|
| `--selftest` | 否 | 单条校验规则能否识别编造 |
| `tests/test_e2e.py` | 否（用 mock） | 整条流水线 + 断言能拦住 mock 埋的坑 |
| 真实调用 | 是 | 实际模型的 JSON 输出质量 |

mock LLM 故意埋了两个问题（第 1 条编造原文、第 2 条数字造假），
端到端测试**断言这两个问题必须被抓到**。这样即使将来改了校验逻辑，
也不会不小心把防线拆掉。

## 七、可扩展方向

- 接入更多厂商（目前已兼容 OpenAI 协议，换 base_url 即可）
- 支持流式输出（长批次时改善体验）
- 校验层扩展：检查命令与输出是否匹配、结果描述是否包含关键状态
- 接入 CI：把 `validate-only` 作为 PR 卡点
